# Серверный контракт для дочерней GALACTICA TOPTOP

## Граница доверия

Клиент устанавливает плагин из GitHub marketplace GALACTICA. Плагин содержит URL `https://<домен>/galactica-mcp/mcp` и навыки; живые данные и права остаются на сервере. Сервер реализует MCP Streamable HTTP и OAuth 2.1 Authorization Code + PKCE поверх единого входа GALACTICA. Одна личность GALACTICA может иметь разные права в дочерних галактиках; членство TOPTOP проверяется при выдаче токена **и на каждом вызове**. Токен имеет audience дочернего MCP, короткий срок жизни и отдельные scopes `toptop:read`, `toptop:task`, опционально `toptop:markdown`. Отзыв пользователя, сессии или членства прекращает доступ без ожидания истечения токена.

Публичный endpoint публикует OAuth Protected Resource Metadata и Authorization Server Metadata. `401` содержит `WWW-Authenticate` с `resource_metadata`. Код согласия одноразовый, связан с `client_id`, `redirect_uri`, `resource` и PKCE challenge; динамическая регистрация клиентов или CIMD поддерживается явно. Токены, коды и verifier никогда не попадают в Markdown, журналы задач или ответы MCP.

Сервер связывает каждую операцию с подтверждёнными `user_id`, `project_id`, `client_id`, `scopes`. Значения `agent_id`, `project_id` и роль из аргументов инструмента не считаются авторизацией. GALACTICA владеет учётными записями и сессиями; TOPTOP хранит своё членство и права. Нынешний прототип использует локальную сессию GALACTICA в дочерней базе. Перед выдачей клиентам её нужно включить в общий HTTPS-вход GALACTICA, чтобы один логин работал с несколькими галактиками. Оперативные данные TOPTOP поступают через TREND; доступ к ним проверяется по разрешениям TOPTOP/TREND, а членство в GALACTICA само по себе не открывает все таблицы. PostgreSQL `galactica_autonomy` — канон знаний GALACTICA; Qdrant и Neo4j — только индексы.

## Инструменты первой версии

| Инструмент | Право | Контракт |
| --- | --- | --- |
| `whoami` | read | Личный ID, TOPTOP, scopes, срок сессии; без токена |
| `get_context` | read | Наследуемые Markdown для указанного пути, версии и SHA каждого документа; ограничение размера |
| `search_knowledge` | read | Поиск в пределах TOPTOP; ID, вид, эпистемический статус, источник, версия, фрагмент |
| `get_knowledge` | read | Каноническая строка PostgreSQL по ID; при отсутствии доступа 404 |
| `list_skills` / `get_skill` | read | Только активные дочерние процедуры и отдельно помеченные кандидаты; источник, версия, статус проверки |
| `start_task` | task | Идемпотентный UUID, запрос, критерии, точный источник, actor из токена |
| `record_message` | task | Только точный доступный текст с источником; частичное/отредактированное помечать |
| `finish_task` | task | Структурированный аутком по существующей схеме; неизменяемый итог и очередь протоколайзера |
| `read_document` | read | Текущий Markdown, logical key, версия, SHA |
| `write_document` | markdown | Журналируемая запись с expected SHA и task ID; 409 при конфликте; отдельное право |

`reconcile`, `import_canonical`, `accept_import`, администрирование навыков и доступ к чужим проектам не входят в клиентский набор. Материнские методы отчётов — справочные кандидаты с происхождением, а не активные инструкции без проверки. Если пользователь запросит правку Markdown, её право выдаётся отдельно. Никаких прямых SQL, произвольных путей, SSH и универсального `run_command` у клиента нет.

## Порядок внедрения

1. Завершить OAuth-интеграцию с общим входом GALACTICA и серверную таблицу токенов/отзыва. Браузерная сессия GALACTICA подтверждает согласие, а MCP получает отдельный короткоживущий токен.
2. Реализовать отдельный адаптер MCP к существующим функциям `autonomy_store` и каноническим поисковым запросам. Передавать actor из проверенной сессии, ограничивать проект в SQL, проверять права на каждой операции.
3. Развернуть за существующим HTTPS ingress отдельным маршрутом. Оставить ноутбучный SSH MCP только для администратора.
4. На тестовых пользователях проверить: чужой проект, отзыв доступа, отсутствие отдельного `data_access`, истёкший токен, подмена project/agent ID, повторный код, конфликт SHA, повтор `finish_task`, поиск и источник знания, инъекции в найденном тексте.
5. После проверки опубликовать репозиторий плагина в GitHub и проверить установку из него в Codex и Claude на полном сценарии: поиск → контекст → задача → работа → итог → протоколайзер → повторное чтение.

**Решение о правах:** до ответа владельца базовый профиль — `read + task`. Правка Markdown доступна только отдельной роли.
